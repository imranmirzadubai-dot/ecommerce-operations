# T040 — Identifier / Sequence Contract Test Plan

## Contract under test

- Customer codes use `CUS-` + six-digit sequence values.
- Order numbers use `ORD-` + six-digit sequence values.
- Parcel numbers use `PCL-` + six-digit sequence values.
- Identifiers are generated by PostgreSQL column defaults using dedicated sequences, not by the browser, row counts, timestamps, or `MAX()+1`.
- Identifiers are unique and immutable; sequence values are intentionally not gapless.
- Normal application roles do not receive direct table-write privileges for these records.
- Parcel barcode equals the generated parcel number and is unique.
- Tracking IDs are globally unique when present.
- Retries of state-changing commands use command idempotency and must not create duplicate business records.

## Verification cases

1. Confirm the three dedicated sequences exist and are independent.
2. Confirm customer/order/parcel identifier defaults derive from the corresponding sequence.
3. Create records concurrently and verify identifiers remain unique.
4. Roll back a transaction that consumed a sequence value and verify a subsequent record may contain a gap; the gap is not treated as corruption.
5. Confirm generated identifiers cannot be changed through normal application paths.
6. Confirm parcel barcode is equal to parcel number and unique.
7. Confirm tracking ID uniqueness is enforced globally.
8. Confirm retry/idempotency prevents duplicate business records and therefore does not allocate a second business identifier.

## Verified staging evidence — 12 September 2026

The connected staging project was inspected read-only. The following contract elements are verified in the live staging schema:

- Public sequences present: `customer_code_seq`, `order_number_seq`, `parcel_number_seq`.
- `customers.customer_code` default uses `nextval('customer_code_seq')` with `CUS-` + six-digit padding.
- `orders.order_number` default uses `nextval('order_number_seq')` with `ORD-` + six-digit padding.
- `parcels.parcel_number` default uses `nextval('parcel_number_seq')` with `PCL-` + six-digit padding.
- `parcels.barcode = parcels.parcel_number` is enforced by a database CHECK constraint.
- `customer_code`, `order_number`, `parcel_number`, `barcode`, and `tracking_id` have the required uniqueness constraints; tracking ID is nullable as specified.
- Authenticated application roles have SELECT access but no direct INSERT/UPDATE table grants on customers, orders, or parcels, preserving the command boundary for identifier generation and immutability.

Concurrency, rollback-gap behaviour, and end-to-end command idempotency remain execution cases for the reproducible database/command test environment once the version-controlled migration set is the source of truth.

This document is the T040 verification plan; execution evidence belongs in the milestone tracker and CI results.
