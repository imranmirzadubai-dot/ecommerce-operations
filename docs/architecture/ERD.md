# Database ERD — v4.0

The v4.0 database is centered on the commercial Order and physical Parcel models.

```text
profiles
  │
  ├──< customers
  │       └──< orders
  │             ├──< order_items ──< parcel_items >── parcels ──> shippers
  │             ├──< parcels
  │             ├──< order_events
  │             ├──< financial_adjustments
  │             ├──< invoice_records
  │             └──  cod_obligations ──< cod_receipts >── parcels
  │
  └── actors on operational/audit records

parcels ──< delivery_outcomes

import_batches ──< import_rows

audit_logs records security-sensitive changes across the domain.
```

## Authoritative ownership

- `orders`: commercial transaction and immutable original amount after confirmation.
- `order_items`: description and ordered integer quantity.
- `parcels`: authoritative current physical lifecycle state.
- `parcel_items`: exact integer allocation from order items to parcels; allocation history is retained.
- `delivery_outcomes`: immutable delivery-attempt/outcome history; NDR is non-terminal.
- `cod_obligations`: order-level expected COD obligation.
- `cod_receipts`: actual collection against a parcel; maximum one receipt per parcel.
- `financial_adjustments`: append-only monetary deltas.
- `order_events`: immutable operational history.
- `audit_logs`: immutable security/change accountability.
- `import_batches` / `import_rows`: staged historical-ingestion lineage.

## Integrity principles

1. One parcel belongs to exactly one order.
2. An order item may be allocated across multiple parcels.
3. Active allocated quantity cannot exceed ordered quantity.
4. Delivered/RTO/Lost/Damaged quantities are derived from parcel allocations and authoritative parcel state; they are not competing editable counters.
5. Original order amount is immutable after confirmation.
6. Historical transactional records are never hard-deleted.
7. Human-readable identifiers are generated server-side from dedicated sequences and are unique/immutable, not gapless.
8. Timestamps are stored in UTC; business-date rendering uses Asia/Dubai.

## Identifier and sequence contract — T040

### Scope

Human-readable operational identifiers are database-generated. UUID primary keys remain the internal relational identifiers; sequence-backed codes/numbers are display and operational identifiers.

### Authoritative sequences

| Identifier | Sequence | Format | Source column | Rule |
|---|---|---|---|---|
| Customer code | `public.customer_code_seq` | `CUS-` + 6-digit zero-padded sequence | `customers.customer_code` | Unique and immutable |
| Order number | `public.order_number_seq` | `ORD-` + 6-digit zero-padded sequence | `orders.order_number` | Unique and immutable |
| Parcel number | `public.parcel_number_seq` | `PCL-` + 6-digit zero-padded sequence | `parcels.parcel_number` | Unique and immutable |

The v4.0 foundation creates these dedicated sequences and uses `nextval()` in server-side column defaults. fileciteturn538file0L2-L2

### Generation rules

1. Identifiers are generated by PostgreSQL, never by the browser or client application.
2. Each identifier domain has its own dedicated sequence; sequences are not shared between customers, orders, and parcels.
3. Generation is atomic under PostgreSQL sequence semantics.
4. Uniqueness is enforced by database `UNIQUE` constraints on the identifier columns.
5. Once assigned, a human-readable identifier is immutable. Business commands must not renumber or rewrite it.
6. A sequence value is not a transactionally gapless business counter. Rollbacks, retries, failed transactions, and concurrent allocation may consume sequence values without creating a corresponding committed row.
7. Gaplessness is therefore not a business invariant and must never be reconstructed by renumbering existing records.
8. Deleted rows are not reused for identifier assignment. The schema uses `ON DELETE RESTRICT` for core historical relationships, and the application does not provide hard-delete operations for transactional records.
9. Display formatting is deterministic from the stored identifier; leading zero padding is presentation formatting, not a separate counter.
10. Identifier generation must remain server-side so clients cannot select, collide with, or forge operational identifiers.

### Barcode and tracking identifiers

- `parcels.barcode` is a required unique value and, in the v4.0 schema, must equal `parcels.parcel_number`. fileciteturn538file0L2-L2
- `parcels.tracking_id` is an externally supplied shipper/carrier identifier. It is nullable until available and globally unique when present through the database `UNIQUE` constraint.
- Tracking IDs are not generated from the parcel sequence and are not rewritten to preserve sequence continuity.

### Invoice identifiers

`invoice_records.invoice_number` is a required unique business identifier. Its generation mechanism is intentionally separate from the customer/order/parcel sequences and must be assigned by the invoice-generation command rather than by a browser client.

### Concurrency and retry behavior

- Concurrent transactions may safely request sequence values; PostgreSQL serializes sequence allocation.
- A command retry must not attempt to regenerate an existing human-readable identifier. Command idempotency determines whether the original result is replayed.
- If a transaction that generated an identifier rolls back, the consumed sequence value may remain unused. This is expected and valid.
- No command may search for `MAX(identifier)+1` or otherwise derive the next identifier from table contents.

### Prohibited behavior

- Client-side identifier generation.
- `MAX(...) + 1` numbering.
- Renumbering after cancellation, deletion, import, or correction.
- Reusing identifiers from failed/rolled-back transactions.
- Treating sequence gaps as data corruption.
- Using one sequence as a surrogate for multiple independent identifier domains.
